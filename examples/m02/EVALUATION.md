**왜 좋았는지:** LLM 초안을 원자료·계산·반례로 점검하고, 예산·휴가 변경까지 반영해 실행 가능한 승인 요청안으로 확정했다.  
**어떻게 해야 좋은지:** 목표·출처·제약을 먼저 주고 생성 → 검산 → 오류 수정 → 명시적 채택을 기록하며, 사전 답안 노출도 정확히 밝힌다.  
**어떻게 실전에 적용할 수 있는지:** 회사 원장·로그의 기간·상태·키를 확인한 뒤 보고·발표 초안을 맡기고, 변경 조건과 승인 권한을 재확인해 제출한다.

# M02 프롬프트 로그·출력물 사후 평가

**판정: 검증·수정 과정을 배우는 우수 사례로 쓸 수 있다. 유일한 정답이나 무결점 제출 예시는 아니다. 제작자 사후 채점은 97.50/100이다.** 좋은 이유는 LLM이 매끄럽게 작문해서가 아니라, 자료의 효력과 제약을 고정하고 실제 오류를 수정한 뒤 변경 조건에서도 실행 가능한 제안을 확정했기 때문이다.

최종 산출물은 요구 표·브리핑·결재 요청을 충족하지만 제출 메타정보의 사전 노출 공개가 불완전하다. 그래서 완전한 제출물이라는 100% 대신 75% 수준, 7.50/10을 선택했다. 이는 **제출 기록의 정확성에 대한 채점자 해석**이며 별도의 자동 실격이나 새로운 총점 상한을 만들지 않았다. 패키지 소개에 사전 노출을 밝혀 둔 사실은 인정하지만, 그것이 당시 EXPORT의 해당 문장을 고치지는 않는다. 동일 문제를 근거·과정 항목에서 다시 감점하지 않았다.

## 사실·계산 검증

아래 계산은 **시험 종료 후 이번 평가에서 실행한 검산**이다. 정답의 타당성을 확인하는 자료이며 응시자가 당시 이 코드를 실행했다고 보지 않는다. 기존 답안 생성기의 값을 불러오지 않고, 체인에 보존된 원자료 표와 이벤트를 직접 파싱했다.

[검산 코드](evaluation/recompute.py) · [전체 48개 상태별 조합 및 직원 배정 검증 결과](evaluation/verification.json)

실행 방법: 저장소에서 `python examples/m02/evaluation/recompute.py`. Python 표준 라이브러리만 사용하며 인접 `verification.json`을 다시 쓴다. 수학 검증이 통과해도 주관적 루브릭 점수가 자동 생성되지는 않는다.

“최적”은 제공된 패키지를 쪼개지 않고, A/B를 유지하며, 예산·스킬·시간 제약 안에서 **제공된 가치점수 합**을 최대화한다는 뜻이다. 실제 ROI나 매출 최대화, 자료에 없는 외주·초과근무까지 포함한 사업 최적안을 뜻하지 않는다. 예산 삭감 단계에서 D를 EMP-02의 DATA 12h에 배정한 것도 가능한 배정이다. 기존 제작자 예시와 직원 이름이 다르다고 오답으로 처리하지 않는다.

## 가장 중요한 개선 세 가지

1. **검증을 재현 가능하게 남기기.** 같은 LLM의 자신감 있는 문장보다 원자료 행·공식·다른 합산 경로·반례 결과가 중요하다. 전수 비교를 했다면 실행 코드와 입력 버전, 실행 결과를 보존한다. 직접 실행하지 못하면 코드 제안과 실제 검증을 구별한다.
2. **최종 제출의 출처와 조건을 점검하기.** 사전 답안 노출, AI 생성 범위, 실제 기록 범위, 누적 이벤트, 승인 요청과 집행의 차이를 마지막 체크에 포함한다. 이번 실행에서는 표뿐 아니라 EXPORT 메타정보도 확인했어야 한다.
3. **실제 원장 탐색을 계산보다 먼저 하기.** v1처럼 정리된 표가 주어지지 않으면 관리 원가센터·주차·승인 상태·유효 revision·직원 키를 정하고 원자료를 회수한다. 출처 파일·행 키와 제외 이유를 남긴 뒤 계산·문서 생성을 맡긴다.

다음은 **사후 작성한 실전용 권장 프롬프트**이다. 실제 12회차 입력으로 위장하지 않는다. 파일명·조건은 해당 회사 자료에 맞게 바꿔야 한다.

```text
결정할 목표와 필수 의무, 승인권자, 예산·시간·스킬 제약을 먼저 정리해줘.
원자료의 기간·상태·키·revision과 승인 효력을 확인하고, 적용한 필터·행 키·단위를 남겨줘.
없는 수치·정책은 만들어 채우지 말고 확인 질문 또는 보류 조건으로 적어줘.
가능한 대안을 같은 기준으로 비교하고, 선택안의 보고서·발표문·질의응답 초안을 생성해줘.
그 뒤 원자료 재합산, 다른 계산 경로, 제안이 실패하는 반례로 핵심 주장을 점검해줘.
직접 실행한 검산과 제안만 한 검산을 구별하고 실행했다면 재현 가능한 결과를 첨부해줘.
새 조건은 이전 조건에 누적 적용해 다시 검토하고, 내가 채택하기 전에는 실행·확정으로 쓰지 마.
최종본에는 AI 생성 범위와 사전 예시 열람 여부, 출처, 미확인 사항, 승인 요청을 정확히 남겨줘.
```

대안적 접근도 가능하다. 누적 변경 후 A+B+C는 26,500, 가치 8점, 여유 500이며 C의 DATA 16h를 EMP-02에 배정하면 제약을 충족한다. 다만 같은 가치점수 최대화 목표에서는 A+B+F보다 낮으므로 “최고 점수 조합”이라고 할 수 없다. AI 파일럿의 전략적 우선순위를 새로 채택할 근거와 승인 조건을 명시한다면 의사결정 대안으로 설명할 수 있다. 목표 변경을 숨기고 정답 숫자만 바꾸는 것은 적절하지 않다.

## 별도 v2 원본 탐색 로그의 평가

[v2 실제 2회차 기록](V2_RETRIEVAL_CHAIN.md)은 같은 에이전트가 CSV를 회수한 별도 연습이다. 97.50/100은 앞선 v1 시험의 점수이며, 이 두 회차에 부여한 점수가 아니다. 최종 시험 산출물·전체 Q&A를 요구하지 않은 추출 연습을 전체 시험처럼 채점하지 않는다.

| 평가 대상 | 관찰·대조 결과 | 판정과 사유 |
|---|---|---|
| 입력값 회수 | 현재 주·AX-POOL·POSTED·BASELINE, 직원 키·휴가 revision 등을 적용해 회수한 주요 합계와 직원/패키지 값이 제작자 Python 검산과 일치 | 이 범위의 결과 정확성 확인. 도구 실행 전체 로그까지 공개된 것은 아님 |
| 최초 출처 명세 | 전표 ID의 범위가 일부 누락되거나 모호했음 | 최초 응답은 합계가 맞아도 추적성 보완 필요 |
| 2회차 정정 | 계정 6100: 1185~1220, 6200: 1221~1238 및 1254·1255, 6300: 1239~1253의 entry_id 숫자 부분을 확인 | 원본 필터 결과와 일치. 출처를 재조회해 고치는 좋은 사례이며 첫 응답의 오류도 남김 |
| 일반화·독립성 | v1 문제를 이미 아는 같은 응시자·모델, 2회차에 문서 효력 재확인 | 낯선 회사에서의 블라인드 탐색 성능이나 전체 v2 시험 성적은 미확인 |

## 확신도와 활용 범위

수치·직원 배정 판정의 확신도는 **높음**이다. 당시 원자료와 최종 출력에서 직접 추출해 재계산했고 3개 조건의 16개 조합씩 비교했다. 채점 수준 선택의 확신도는 **보통**이다. 공개 앵커에 근거했지만 제작자 본인의 해석이며 독립 채점자 간 일치도를 측정하지 않았다. 특히 최종 산출물의 메타정보 오류를 어느 수준에 반영할지는 다른 채점자가 원문을 보고 재판단할 수 있다.

활용 목적은 “이 숫자를 외우기”보다 **LLM 초안을 어떻게 검사하고 조건 변화에 맞춰 수정·확정하는지 배우기**이다. 무결점 답안, 인간 능력의 점수, 다른 모델보다 우수하다는 근거, 실제 기업 의사결정의 보증으로 사용하지 않는다. 블라인드 응시 기록·독립 채점·실제 시간 측정은 별도 실행이 필요하다.
